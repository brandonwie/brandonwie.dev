프론트엔드 컴포넌트, 백엔드 API 라우트, 테스트 파일을 동시에 건드리는 큰
리팩토링 작업을 하고 있었어요. 단일 Claude Code 세션에서 파일 간 전환은 지속적인
컨텍스트 스위칭을 의미했고, 컨텍스트 윈도우가 빠르게 차고 있었습니다. 여러
터미널 탭을 열 수 있다는 건 알았지만, 그 세션들은 상태를 공유하거나 작업을
조율할 수 없었어요. Agent teams가 바로 이 문제를 해결합니다.

## Agent Teams란

Agent teams는 하나의 세션("리드")이 여러 팀원 세션을 생성할 수 있는 실험적
Claude Code 기능입니다. 각 팀원은 자체 컨텍스트 윈도우와 도구 세트를 갖고
실행되지만, 작업 목록을 공유하고 서로 메시지를 보낼 수 있어요.

핵심 개념:

- **리드** -- 팀을 만들고, 팀원을 생성하고, 작업을 조율하는 메인 세션
- **팀원** -- 각자 자체 컨텍스트 윈도우를 가진 별도의 Claude 인스턴스
- **작업 목록** -- 상태(대기, 진행 중, 완료)와 의존성이 있는 공유 작업 항목
- **메일박스** -- 리드에게만이 아닌 모든 에이전트 간 직접 메시징

Subagent와는 다릅니다. Subagent는 한 번 던지고 결과만 받는 방식이에요. 팀원은
협업합니다. 서로 질문하고, 블로커를 보고하고, 공유 자원에 대해 조율할 수
있어요.

## Teams vs Subagents vs Solo 선택 기준

결정 프레임워크는 간단합니다:

| 필요                            | 사용       |
| ------------------------------- | ---------- |
| 빠른 집중 작업, 결과만 중요     | Subagent   |
| 작업자들이 토론하고 협업해야 함 | Agent team |
| 순차 작업, 같은 파일 편집       | Solo 세션  |

Agent teams에 가장 적합한 경우는: 병렬 코드 리뷰(관심사별 리뷰어 한 명), 경쟁적
가설 디버깅(각 팀원이 다른 이론 테스트), 크로스 레이어 조율
(프론트엔드/백엔드/테스트), 독립 모듈 개발입니다.

처음에는 subagent가 더 적합한 작업에 agent teams를 사용했어요. 팀을 생성하고,
작업 목록을 관리하고, 팀원 진행 상황을 모니터링하는 조율 오버헤드가 빠르고
집중적인 작업에는 가치가 없었습니다. 규칙: 솔로로 5분 이내면 subagent를
사용하세요. 팀원들이 서로 대화해야 하면 team을 사용하세요.

## 설정하기

`settings.json`에서 기능을 활성화합니다:

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

표시 모드를 선택합니다:

```json
{
  "teammateMode": "in-process"
}
```

두 가지 모드가 있어요: `"in-process"` (팀원이 같은 터미널에서 실행, 출력 인터리빙)
와 `"tmux"` (각 팀원이 자체 패널). tmux 설정이 필요 없어서 `"in-process"`를
사용하지만, 여러 팀원을 동시에 모니터링하려면 `"tmux"`가 더 좋습니다.

## 효과적인 패턴들

**Delegate 모드 (Shift+Tab)** 는 리드를 조율만 하도록 제한합니다. 리드는 아무것도
구현할 수 없고, 작업 목록 관리와 팀원과의 소통만 가능해요. 위임해야 할 작업을
리드가 직접 하는 병목을 방지합니다.

**계획 승인**은 팀원이 먼저 읽기 전용 모드에서 계획을 세우는 패턴입니다. 리드가
계획을 검토하고, 승인 후에야 팀원이 구현으로 전환합니다. 코드가 작성되기 전에
오해를 일찍 잡아줘요.

**작업 크기 조정**이 중요합니다. 팀원당 5-6개 작업을 목표로 하세요. 너무 적으면
팀원이 빨리 끝나고 유휴 조율 오버헤드가 생겨요. 너무 많으면 작업이 끝나기 전에
컨텍스트 윈도우가 차버립니다.

**품질 훅**은 조기 완료를 방지합니다. `TeammateIdle` 훅은 유휴 팀원에게 완료
보고 대신 계속 작업하라고 합니다. `TaskCompleted` 훅은 완료로 표시하기 전에
작업이 실제로 끝났는지 검증합니다.

## 어렵게 배운 것들

**in-process 모드에 세션 복구가 없습니다.** 팀원이 크래시하거나 터미널이 닫히면
작업이 사라져요. 터미널 탭을 실수로 닫고 나서야 발견했습니다. 작업이 한 번에
끝나지 않을 수 있다면, 인계 문서와 함께 solo 세션을 대신 사용하세요.

**권한 상속이 전부 아니면 전무입니다.** 팀원은 생성 시 리드의 권한 모드를
상속합니다. 한 팀원에게는 읽기 전용(리뷰용), 다른 팀원에게는 읽기/쓰기
(구현용)를 줄 수 없어요. 모든 팀원이 같은 권한을 받습니다.

**중첩 팀이 안 됩니다.** 팀 안에서 팀을 만들 수 없어요. 워크플로우에 계층적
위임(리드가 서브 리드를 생성하고 서브 리드가 팀원을 생성)이 필요하면 수동
멀티 세션 조율을 사용해야 합니다.

## 제한 사항

- in-process 팀원에 세션 복구 없음
- 세션당 한 팀, 중첩 팀 불가
- 고정 리드 (리더십 이전 불가)
- 모든 팀원이 생성 시 리드의 권한 모드 상속
- 분할 패널에 tmux 또는 iTerm2 필요

## 예시 프롬프트

리뷰 팀을 생성하는 예시입니다:

```text
Create an agent team to review PR #142. Spawn three
reviewers:
- One focused on security implications
- One checking performance impact
- One validating test coverage
Have them each review and report findings.
```

각 리뷰어가 자체 컨텍스트에서 독립적으로 PR의 다른 부분을 읽으며 작업합니다.
관련 이슈를 발견하면 서로 메시지를 보낼 수 있고, 결과를 리드에게 보고합니다.

## Agent Teams를 사용하면 안 되는 경우

- **같은 파일의 순차 편집** -- 팀원이 같은 파일을 동시에 안전하게 편집할 수
  없습니다. Solo 세션을 대신 사용하세요.
- **빠른 일회성 작업** -- 솔로로 5분 이내면 조율 오버헤드가 가치 없어요. 집중
  위임에는 subagent를 사용하세요.
- **세션 지속성이 필요할 때** -- in-process 팀원은 중단되면 복구할 수 없습니다.
  장시간 작업에는 인계 문서와 함께 solo 세션을 사용하세요.
- **중첩 조율** -- 팀 안에서 팀을 만들 수 없어요. 계층적 워크플로우에는 수동
  멀티 세션 조율을 사용하세요.

## 핵심 정리

Agent teams는 에이전트 간 소통이 도움되는 진정한 병렬 작업이 있을 때 빛납니다.
설정은 최소한(환경 변수 하나)이지만, 진짜 실력은 올바른 도구를 선택하는 것이에요:
순차 작업에는 solo, 빠른 위임에는 subagent, 협업 병렬 작업에는 teams.
Delegate 모드로 시작해서 조율 역할에 집중하고, 팀원당 5-6개 작업으로 크기를
조정하고, in-process 모드에는 크래시 복구가 없다는 걸 기억하세요.
